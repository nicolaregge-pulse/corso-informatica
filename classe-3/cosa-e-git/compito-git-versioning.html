Obiettivo: dimostrare che hai capito cos'è Git e come funzionano le versioni, con parole tue. Conta la comprensione, non le frasi perfette.
Ripasso lampo (prima di rispondere)
  1. Git = la "macchina del tempo" del progetto: salva le modifiche (i commit) e ti fa tornare indietro.
  2. Git è lo strumento; GitHub è il sito-servizio dove tieni il progetto online. GitHub è una piattaforma (PaaS), della famiglia dei servizi …aaS (IaaS, PaaS, SaaS), e si paga in Freemium (base gratis, extra a pagamento).
  3. repository = la cartella-progetto con la storia · branch = una strada parallela per provare · merge = unirla di nuovo al ramo principale.
  4. Versioning: le versioni si scrivono v1.2.3 (1 = cambiamento grosso, 2 = funzione nuova, 3 = correzione bug). Una versione pubblicata non si riusa più.

Italiano

Apri un documento nuovo: nel browser vai su docs.new e dai un titolo (es. "Git e Versioning — Nome Cognome"). Rispondi alle tre parti.

Parte 1 — Git (con parole tue)

  1. Cos'è Git e a che problema serve? (2-3 frasi)
  2. Spiega questi termini con una frase ciascuno: repository, commit, branch, merge.
  3. Qual è la differenza tra Git e GitHub?

Parte 2 — Versioning (ragiona)

Le versioni si scrivono come vX.Y.Z (X = cambiamento grosso, Y = funzione nuova, Z = correzione bug). Un gioco è alla versione v1.2.0. Scrivi quale sarà la nuova versione in ciascun caso e perché:

  1. Correggi un piccolo bug. → nuova versione: ______
  2. Aggiungi un nuovo livello al gioco (le cose vecchie funzionano ancora). → ______
  3. Riscrivi tutto da capo con un motore nuovo, incompatibile col vecchio. → ______

Poi guarda questo grafo e rispondi: quanti branch vedi oltre al main? Quanti merge? A cosa serviva il ramo rosso?

Parte 3 — La tua esperienza

  1. Racconta cosa hai fatto oggi con GitHub (es. creare l'account, entrare). Cosa è stato facile, cosa difficile?
  2. Fai un esempio tuo, non del gioco: in quale altra situazione (una tesina, delle foto, un progetto) sarebbe utile avere la "storia delle versioni"?

Quando hai finito, consegna il documento su Classroom.

বাংলা

লক্ষ্য: নিজের ভাষায় দেখাও যে তুমি বুঝেছ Git কী এবং ভার্সন কীভাবে কাজ করে। নিখুঁত বাক্য নয়, বোঝাটাই গুরুত্বপূর্ণ।
ঝটপট ঝালাই (উত্তর দেওয়ার আগে)
  1. Git = প্রজেক্টের "টাইম মেশিন": পরিবর্তন (commit) সংরক্ষণ করে এবং পেছনে ফিরে যেতে দেয়।
  2. Git হলো টুল; GitHub হলো সেই সাইট-সার্ভিস যেখানে প্রজেক্ট অনলাইনে রাখো। GitHub একটি প্ল্যাটফর্ম (PaaS), …aaS পরিবারের (IaaS, PaaS, SaaS), এবং Freemium মডেলে চলে (বেসিক ফ্রি, অতিরিক্ত টাকায়)।
  3. repository = ইতিহাসসহ প্রজেক্ট-ফোল্ডার · branch = পরীক্ষা করার সমান্তরাল পথ · merge = আবার মূল শাখায় যুক্ত করা।
  4. Versioning: ভার্সন লেখা হয় v1.2.3 (১ = বড় পরিবর্তন, ২ = নতুন ফিচার, ৩ = বাগ সংশোধন)। প্রকাশিত ভার্সন আর ব্যবহার করা হয় না।

একটি নতুন ডকুমেন্ট খোলো: ব্রাউজারে docs.new-এ যাও এবং একটি শিরোনাম দাও (যেমন "Git ও Versioning — নাম ও পদবি")। তিনটি অংশের উত্তর দাও।

অংশ ১ — Git (নিজের ভাষায়)

  1. Git কী এবং এটি কোন সমস্যার সমাধান করে? (২-৩ বাক্য)
  2. প্রতিটি শব্দ এক বাক্যে ব্যাখ্যা করো: repository, commit, branch, merge।
  3. Git ও GitHub-এর পার্থক্য কী?

অংশ ২ — Versioning (চিন্তা করো)

ভার্সন লেখা হয় vX.Y.Z হিসেবে (X = বড় পরিবর্তন, Y = নতুন ফিচার, Z = বাগ সংশোধন)। একটি গেম v1.2.0 ভার্সনে আছে। প্রতিটি ক্ষেত্রে নতুন ভার্সন কী হবে এবং কেন লেখো:

  1. একটি ছোট বাগ ঠিক করলে। → নতুন ভার্সন: ______
  2. গেমে একটি নতুন লেভেল যোগ করলে (পুরনো জিনিস এখনও কাজ করে)। → ______
  3. সম্পূর্ণ নতুন করে, পুরনোর সাথে বেমানান একটি নতুন ইঞ্জিন দিয়ে লিখলে। → ______

তারপর এই গ্রাফটি দেখে উত্তর দাও: main ছাড়া কতটি branch দেখছ? কতটি merge? লাল শাখাটি কী কাজে লেগেছিল? (গ্রাফটি উপরের ইতালীয় অংশে আছে)

অংশ ৩ — তোমার অভিজ্ঞতা

  1. আজ GitHub দিয়ে কী করেছ বলো (যেমন অ্যাকাউন্ট তৈরি, লগইন)। কী সহজ ছিল, কী কঠিন?
  2. গেম ছাড়া তোমার নিজের একটি উদাহরণ দাও: আর কোন পরিস্থিতিতে (একটি রচনা, ছবি, একটি প্রজেক্ট) "ভার্সনের ইতিহাস" থাকা উপকারী হতো?
